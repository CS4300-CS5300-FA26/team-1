# Use Django's built-in User model, sessions, and password hashing for authentication
Date: 2026-10-22

## Status
Accepted

## Decision
FitPro authenticates users with Django's built-in `django.contrib.auth` `User` model, server-side sessions (the database session backend), and Django's default PBKDF2-SHA256 password hasher. Auth lives in the `accounts` app. Users log in with their email address (or username) through a `LoginForm` that subclasses `AuthenticationForm`. Profile data that `User` doesn't have (onboarding answers, weight, and so on) lives in `core.UserProfile`, a one-to-one model linked to `User`.

## What this offers
* Secure defaults: salted password hashing, session key rotation on login (prevents session fixation), CSRF protection, `HttpOnly` cookies, and safe `next` redirects, with no extra code.
* Less code to write and test: registration, login, and logout reuse `UserCreationForm`, `AuthenticationForm`, `LoginView`, and `LogoutView`.
* Fits the rest of the stack: the admin site, `login_required`, and `request.user` all work with the built-in model, and sessions are stored in the existing PostgreSQL database, so no new infrastructure is needed.
* Password rules come from `AUTH_PASSWORD_VALIDATORS` (minimum 10 characters, not common, not numeric, not similar to the username or email).

## Tradeoffs considered
* Custom user model (`AUTH_USER_MODEL`): would let email be the login field and be unique in the database. Django recommends one at the start of a project, because switching later is hard. We kept the built-in model so the D-1 story could ship on the schema that was already deployed. Email login and email uniqueness are handled in the forms instead, so uniqueness is not enforced by the database (two simultaneous sign-ups with the same email could both succeed). This is listed as a known gap in the README.

> **Update 2026-10-29:** Rate limiting and email uniqueness have since been addressed. Throttling is in [ADR-006](adr-006.md). Email uniqueness is now enforced by the database through a unique index on `LOWER(email)` (migration `accounts/0002_unique_email_index`), and a sign-up that loses a race shows the usual "already exists" error. The text above is kept as the original decision record.
* Token / JWT auth (for example with Django REST framework): useful for a separate frontend or mobile app, but FitPro is server-rendered, and tokens stored in the browser are easier to steal than `HttpOnly` session cookies. Rejected for now. It can be added for an API later without replacing sessions.
* Third-party login (OAuth, `django-allauth`): adds a dependency and setup with each provider. Not needed for the class project. It could be added on top of the built-in model later.
* Argon2 password hashing: stronger than PBKDF2, but needs the `argon2-cffi` dependency. Django's default is acceptable for now, and existing hashes upgrade automatically on the next login if we switch.
