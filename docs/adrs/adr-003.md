# Deploy FitPro on GKE Autopilot
Date: 2026-10-01

## Status
Accepted

## Decision
We will deploy FitPro to a single GKE Autopilot cluster in us-central1, with one production namespace, backed by Cloud SQL for PostgreSQL. Container images are stored in Artifact Registry and deployed by GitHub Actions on merge to main, authenticating with Workload Identity Federation. Infrastructure is managed with Terraform, run locally by the GCP account owner.

## What GKE Autopilot offers
* Always on: pods run continuously, so there are no cold starts, and the grader sees consistent behavior. Two replicas with rolling updates and a PodDisruptionBudget keep the app up during deploys.
* Room to grow: background workers, websockets, or scheduled jobs can be added later without changing platforms.
* Managed nodes: Google provisions, scales, and patches the nodes. The team writes code and merges PRs; nobody manages Kubernetes day to day.
* Fits the budget: one cluster's management fee is covered by the GKE free tier, and Autopilot bills on pod resource requests, so a small app stays inexpensive.
* Keyless CI/CD: GitHub Actions authenticates through OIDC and Workload Identity Federation, and pods use Workload Identity, so no long-lived keys live in GitHub or the cluster.
* Simple rollback: images are tagged by git SHA, so `kubectl rollout undo` restores the previous version.
* Learning goal: hands-on experience with GKE.
* If the image breaks, the production pods never get replaced, therefore inherent protection against downtime.

## Tradeoffs considered
* Cloud Run: cheaper with scale-to-zero, but cold starts are a risk for grading, and long-running workers or websockets fit poorly. Keeping one instance warm removes cold starts but not the workload limits.
* VM with Docker Compose: the cheapest always-on option, but a single point of failure with manual OS patching, and CI deploys would typically need an SSH key stored in GitHub. The free-tier e2-micro (1 GB RAM) is too small for Django, Postgres, and Docker together.
* Complexity: Kubernetes manifests add concepts the team does not otherwise need. Mitigated by keeping manifests small.
* No staging environment: one namespace keeps cost down. Kustomize overlays (base plus prod) allow adding staging later without restructuring.
* Database availability: Cloud SQL runs without high availability to save cost, so it is a single point of failure. Mitigated with automated backups, deletion protection, and a deploy freeze before grading.
* No domain yet: the app is served over HTTP on a reserved static IP. A domain, managed TLS, and host-based routing come in a later iteration.
* Trial window: the $300 credit expires 90 days after signup ending after finals week. All resources are destroyed with Terraform at semester end.
