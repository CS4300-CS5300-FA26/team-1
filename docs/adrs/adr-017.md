# Send account email through Resend's free tier
Date: 2026-11-20

## Status
Accepted. Part of issue #62 (email verification and password reset), which closes security assessment findings F-3
and F-5 ([ADR-016](adr-016.md)). The mailer is implemented (`core/mail.py`, `accounts/emails.py`); the verification
and reset flows that use it follow on the same branch.

## Decision
Account email (sign-up verification, "you already have an account" notices, password reset) is sent through
[Resend](https://resend.com) on its free transactional plan.

| Part | Decision |
| --- | --- |
| Account | A dedicated Resend account for FitPro, not a team or domain inside an account used for other projects, because a free team's quota is shared across all of its domains. The owner and who has access are listed in the README infrastructure section, next to the Spotify app |
| Plan and limits | Free: 100 emails a day and 3,000 a month. Sent and received emails both count, and the daily quota resets at midnight UTC. No inbound email is set up, so only sends count |
| Sending domain | `fitpro-app.tech`, verified in Resend. The SPF and DKIM records Resend issues (and a DMARC record) go in Cloudflare as DNS-only records, like the existing ones (ADR-004) |
| API key | Sending access only, restricted to `fitpro-app.tech`. Stored in Secret Manager as `fitpro-resend-api-key` through Terraform (an empty secret filled with `gcloud`, the same pattern as the Spotify client secret) and read with `read_secret()`; `.env` locally. Tests never get a key |
| Transport | Resend's HTTP API (`POST https://api.resend.com/emails`, `Authorization: Bearer <key>`) through `core.mail.ResendEmailBackend`, a `BaseEmailBackend` subclass selected in `MAILERS` that uses the standard library's `urllib`, as `spotify/client.py` does. It sends the `User-Agent` header Resend requires, a 10-second timeout, and an `Idempotency-Key` made from a SHA-256 hash of the request body, so the same email retried within 24 hours is sent once. It supports text, HTML, cc, bcc, reply-to, and extra headers, refuses attachments, and refuses CR/LF in any header value |
| Mailer selection | Tests: Django's in-memory mailer. Local development without a key: the console mailer. Everywhere else, including production with the key missing: the Resend backend, which then fails every send with a logged error. Production never falls back to printing email, so verification and reset links can't end up in the logs, and `manage.py check --deploy` in CI now includes the `mail` checks (`mail.E001` fails on a development-only mailer) |
| Calling it | `accounts.emails.send_account_email(to, subject, text, html=None)` applies the per-recipient limit, sends, and returns False on any failure. The account flows call it from a background thread pool so no response waits for Resend, and they never show whether an email went out ([ADR-018](adr-018.md)) |
| Send limit | A new per-recipient throttle, `AUTH_THROTTLE['email_recipient'] = (5, 60 * 60)`: 5 emails per address per hour, keyed on a hash of the lowercased address. It sits on top of the existing per-IP registration limit, so the forms can't be used to spam one inbox or burn the day's quota quickly. A send that fails gives its count back (nothing reached the inbox), so transient failures don't lock an address out. With no real user base yet, 5 an hour covers a person retrying a verification or reset several times |
| Tests | No test ever calls Resend. Tests use Django's in-memory (`locmem`) mailer through `MAILERS`, so sent mail can be inspected in `django.core.mail.outbox`. The Resend backend's own unit tests mock the HTTP call (`urlopen`) to simulate success, each quota code, `rate_limit_exceeded`, a timeout and a 5xx, and CI never gets an API key |

### When the quota runs out
Resend answers HTTP 429 with an error code: `daily_quota_exceeded`, `monthly_quota_exceeded`, or
`rate_limit_exceeded` (too many requests per second).

* **What the user sees:** the usual "check your email" page on every form that sends account email, whether or not
  the email went out, so a failure can't reveal which addresses have accounts. The emails are sent in the background,
  so it can't show in the response time either ([ADR-018](adr-018.md)). Quotas and the provider are never mentioned.
* **What we log:** the backend logs quota exhaustion separately from other failures, on the `fitpro.email` logger at
  ERROR: "Email quota exhausted (daily_quota_exceeded): email is not being sent until the quota resets", and raises
  `EmailQuotaExceeded`. A rejected key or sender (401/403) and a missing key are also logged at ERROR, pointing at the
  configuration. `rate_limit_exceeded`, network errors, timeouts, and 5xx responses are logged at WARNING. Log lines
  never include the recipient address, the subject, the body, a link token, or the API key, and error codes from the
  network are cut to printable characters so they can't inject log lines.
* **Alerting:** a Cloud Monitoring log-based alert on the quota log line, so whoever is on call finds out before
  users report it.

## What this offers
* **No cost** at our volume. A class signing up together (about 30 to 40 verification emails) fits in a day's quota
  with room to spare.
* **Simple setup:** one dashboard, one domain verification, one API key. No IAM, no sandbox approval, no new cloud
  account to manage.
* **No new Python dependency.** The backend is one HTTPS POST using the standard library, following the existing
  Spotify and OpenAI clients.
* **Precise failure handling.** The API's error codes let us tell "out of quota" from "Resend is down", which the
  logging rule above needs.
* **Isolation.** A dedicated account means FitPro's sign-ups can't use up another project's quota, or the reverse,
  and teardown at the end of the semester is: delete the account, the secret, and the DNS records.

## Tradeoffs considered
* **The 100-a-day cap is the main cost.** Every verification, notice, and reset email counts. Once it's reached,
  nobody can verify an email or reset a password until midnight UTC (5 p.m. in Colorado Springs during standard
  time). The per-IP and per-recipient limits slow abuse but can't stop someone using many IPs and addresses.
  Upgrading to a paid plan removes the daily limit; we'd revisit if the quota alert fires more than once.
* **SMTP through Django's built-in backend:** no custom code at all, since the Resend API key doubles as the SMTP
  password (`smtp.resend.com`, port 587; GCP blocks outbound port 25). Rejected as the default because Resend doesn't
  document how quota errors appear over SMTP, so we couldn't log "out of quota" reliably. It stays as a fallback.
* **The `resend` Python SDK:** a new dependency for a single POST request. Rejected.
* **SendGrid, Mailgun, or Mailjet:** the third-party providers Google's documentation points to, since Google Cloud
  has no transactional email service of its own. They would work the same way; Resend wins on setup simplicity and
  the team's prior experience with it.
* **Amazon SES:** cheapest per email at scale, but a second cloud account with its own IAM and a sandbox to request
  production access from. Too much setup for our volume.
* **Google Workspace SMTP relay:** needs a paid Workspace domain, which we don't have.
* **Running our own mail server:** rejected. GCP blocks outbound port 25, and a new server's IP has no sending
  reputation, so mail would land in spam.
* **Known limits:**
  * The backend sends during whatever thread calls it, with a 10-second timeout that it treats like any other send
    failure. The account flows call it from a background thread so pages don't wait ([ADR-018](adr-018.md)).
  * Resend sees every recipient address and email body. Bodies hold only a link and generic text, never profile data.
  * The backend builds the JSON request itself rather than calling `EmailMessage.message()`, so it must reject CR/LF
    in the subject and addresses (Django's header-injection check doesn't run for custom backends that skip it).
