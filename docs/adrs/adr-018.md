# Confirm every account's email, and reset passwords by email
Date: 2026-11-20

## Status
Accepted. Issue #62. Closes security assessment findings F-3 (registration revealed which emails and usernames have
accounts) and F-5 (email ownership was never verified), together with [ADR-017](adr-017.md) (Resend). Updates
[ADR-006](adr-006.md), [ADR-010](adr-010.md), and [ADR-016](adr-016.md); dated notes there point here.

## Decision
Every account must confirm its email before it can be used, whether it was created with a password or with "Sign up
with Spotify". Users can reset a forgotten password by email.

| Part | Decision |
| --- | --- |
| Unconfirmed accounts | A new account is created with `is_active=False` and activated when its email is confirmed. Django's `ModelBackend` refuses inactive users, so an unconfirmed account can't log in with a password, can't keep a session, and Spotify login refuses it too ("Confirm your email first"). No new model or migration: "active" means "email confirmed" (FitPro has no other way to deactivate an account) |
| Sign-up | `POST /accounts/register/` never logs anyone in and never says an email is taken. A new address gets an inactive account and a confirmation link. An address that already has an account gets an email telling its owner so, with log-in and reset links, and no account is created. Both show the same "Check your email" page. Usernames are public and are still checked on the form |
| Confirmation link | `/accounts/verify/<uid>/<token>/`, signed with its own salt on Django's `PasswordResetTokenGenerator` (`accounts.tokens`). The token hashes `is_active` and the email, so it stops working once used. Opening the link (GET) only shows a "Confirm my email" button; the POST activates the account and logs in (rotating the session key). Email security scanners open links in messages, and a GET that confirmed would let them do it |
| Resend | `/accounts/verify/resend/` sends a new link to an unconfirmed sign-up. Unknown and already-confirmed addresses get the same page and no email |
| Expiry and cleanup | Both kinds of link expire after `PASSWORD_RESET_TIMEOUT`, set to 24 hours, and are single use. An unconfirmed sign-up older than that (never logged in) is deleted when someone next signs up or asks for a link, so it stops holding its username and email |
| Password reset | `/accounts/password/reset/` emails a link with Django's own reset token; `/accounts/password/reset/<uid>/<token>/` is Django's `PasswordResetConfirmView`, which moves the token into the session before showing the form. Changing the password signs out the account's other sessions (Django's session auth hash). Unlike Django's default, accounts with no password (Spotify sign-ups) and unconfirmed accounts can reset too, because control of the inbox is what proves ownership |
| Reset of an unconfirmed account | It confirms the email. Because someone else may have created the account with this address (Spotify doesn't verify emails), any Spotify link on it is removed first and the event is logged at WARNING on `accounts.security`. Only the inbox owner keeps access |
| Spotify sign-up | Creates the account inactive, with no password, and emails the confirmation link to the Spotify email ("Someone signed up for FitPro with a Spotify account that uses this address"). A Spotify account that shares no email is refused. After confirming, the user is asked to set a password, as before (ADR-010) |
| Sending | All four emails go through `accounts.emails` and `send_account_email()` (ADR-017): plain text, links built from the request (limited to our hosts by `ALLOWED_HOSTS`), and at most 5 per address per hour. A send that fails gives its count back, so transient failures can't lock an address out of the emails it needs |
| Existing accounts | Accounts created before this change are active and never confirmed their email, and this change doesn't touch them. FitPro has no real users yet, so the user tables are dropped when this is deployed and every account that exists afterwards went through confirmation. If accounts ever had to be kept across this change, a data migration would need to deactivate them (they'd then confirm through "Forgot password" or the resend page) |
| Rate limits | Sign-up keeps its per-IP limit (50 an hour). "Forgot password" and "resend confirmation" share a new per-IP limit, `AUTH_THROTTLE['email_request']`, 20 an hour |
| When an email can't be sent | Sign-up (password or Spotify), **forgot password**, and **resend confirmation** always show their usual "check your email" page, whether or not the email went out. An error that appeared only for some addresses would reveal which have accounts. A sign-up whose link couldn't be sent is kept, so the person can use "Send the link again" once email works (it expires after 24 hours like any unconfirmed sign-up). The pages say to try again later and to contact us if nothing arrives. Failures are logged on `accounts.security` with a user id, never the address, and the cause (quota, outage, the per-address limit) by the mailer |
| Response timing | The same forms only email some addresses, so waiting for Resend (up to its 10-second timeout) would make some answers slower and reveal accounts. `accounts.emails` builds each email during the request and hands it to a small background thread pool (`ThreadPoolExecutor`, 2 threads per Gunicorn worker) that sends it and logs any failure; the response never waits. Sign-up also hashes the submitted password for an address that already has an account, as a new sign-up does, so both take the same time (Django's login does the same for unknown users). `ACCOUNT_EMAIL_IN_BACKGROUND` is off in tests, which send inline |

## What this offers
* **Every account's email is proven.** Nobody can use an address they don't control, so the squatting in F-5 no
  longer gets anyone in, and an owner whose address was claimed recovers it with "Forgot password".
* **No pre-hijacking through Spotify.** Recovering a claimed address removes the claimer's Spotify link, so they
  can't log back in with Spotify after the owner takes it over (the risk the assessment flagged in F-5).
* **Sign-up no longer lists emails.** The page is identical whether or not an address has an account (F-3); the
  owner hears about the attempt by email instead.
* **Built on Django.** Token signing, expiry, the reset views, session invalidation, and inactive-user handling are
  Django's own, with no new dependency or migration.

## Tradeoffs considered
* **Showing an error when an email can't be sent:** the team first chose a generic server error on every form, so a
  person waiting for an email that will never come knows to contact us. Two PR reviews showed it reveals accounts.
  "Forgot password" and "resend confirmation" only send, and only count toward the 5-per-address limit, for addresses
  with an account, so the error there appeared only for registered addresses. And because those requests can use up a
  registered address's limit, sign-up then answered 503 for it but the normal page for an unknown address. Every form
  now shows its usual page and logs the failure. The cost: someone whose email failed sees "check your email" and has
  to try again or contact us, which the pages tell them.
* **A durable task queue for the emails** (Django 6's tasks framework with a third-party backend, or Celery): survives
  restarts and retries failures, but needs a separate worker process and a queue store in Kubernetes. Django's own
  backends run tasks immediately or not at all. A background thread is enough for a few emails an hour; revisit if
  emails get lost in practice.
* **Usernames are still enumerable** on the sign-up form ("A user with that username already exists"). They're
  public handles, not login secrets. Those answers keep ADR-016's cap of 10 per IP per hour (`register_taken`), and
  the login throttle (ADR-006) limits guessing against the accounts.
* **Logging users in at sign-up and gating every page until they confirm:** rejected. Inactive accounts are refused
  everywhere by Django already, so no page can forget the check, and nothing differs between new and existing
  addresses at sign-up.
* **A separate "pending sign-up" table instead of inactive users:** keeps unconfirmed sign-ups from holding a
  username or email at all, but adds a model, a migration, and a second place accounts live. The 24-hour cleanup
  gets most of the benefit.
* **`django-allauth`:** covers all of this and more, but replaces the existing auth views and adds a large
  dependency (AGENTS.md: don't add one when Django covers the need).
* **Known limits:**
  * "Every account is confirmed" relies on the user tables being dropped at deployment (see "Existing accounts").
  * A send that times out is given back even though Resend may have accepted it, so in that rare case an address can
    get one email over the per-address limit.
  * Queued emails live in the worker's memory. Python finishes them when a worker shuts down normally, but a worker
    killed outright (Gunicorn's timeout, an out-of-memory kill) loses its queue; the person sees "check your email" and
    has to ask again.
  * Someone who receives a confirmation email for a Spotify sign-up they didn't make, and confirms it anyway, hands
    that account to whoever made it. The email says to ignore it if it wasn't them.
  * Confirmation is one-way: there's no "change my email" flow yet, so the address can't be changed after sign-up.
  * Links are plain text in the email; no HTML version yet.
