# Remove the Django admin site
Date: 2026-10-29

## Status
Accepted. Supersedes the admin-related parts of [ADR-005](adr-005.md) ("the admin site ... work[s] with the built-in model") and closes the "admin site is reachable on the public hostname" known gap.

## Decision
`django.contrib.admin` is removed from `INSTALLED_APPS`, the `/admin/` route is removed from `fitpro/urls.py`, and `/admin/` now returns 404. Both lines are left commented out (marked "see ADR-007"), and `core/admin.py` (which registers `UserProfile`) is kept. Nothing imports it while the admin app is not installed, so it has no effect.

To re-enable: uncomment the `admin` import and `path('admin/', ...)` in `fitpro/urls.py`, and uncomment `'django.contrib.admin'` in `INSTALLED_APPS`. No migration is needed. Read the network-restriction note under Alternatives first. `django.contrib.auth`, sessions, and the `User` model are unchanged.

## Why
* No requirement uses it. Users sign up, log in, and edit their own data through the app's own pages; no user story needs staff to edit records in a browser.
* It was the most attractive brute-force target on the site: a well-known path, a password-only login, and accounts with full read/write access to every user's data. The rate limiting from [ADR-006](adr-006.md) covers only `accounts` views; the admin login had its own unthrottled form.
* Removing it is safer than hardening it. A route that doesn't exist can't be guessed, misconfigured, or hit by a future Django admin vulnerability.

## Consequences
* There is no browser UI for inspecting or fixing data. Use `manage.py shell` (locally, or a one-off Kubernetes Job using the same image and secrets as the migrate Job) and Cloud SQL access controlled by IAM.
* `createsuperuser` still works, but staff/superuser flags no longer grant access to anything in the app.
* Existing `django_admin_log` table and the admin migration records stay in the database. They are harmless; nothing reads them, and `migrate` leaves them alone. Drop the table later only if desired.
* `core/admin.py` is dead code until the admin is re-enabled. Tests that used `/admin/` as an example path now use `/users/` and `/dashboard/`.

## Alternatives considered
* **Keep admin, add throttling:** needs custom login view wiring for `AdminSite`, and still leaves a high-value public target. Rejected.
* **Keep admin on an obscure path or behind IP allow-listing / IAP:** obscurity is weak, and allow-listing needs load balancer or Gateway changes we have no need to maintain right now. This remains the way to bring it back if staff tooling is ever required: restrict at the network layer first, then re-add the app and route, and require staff accounts to use strong unique passwords.
