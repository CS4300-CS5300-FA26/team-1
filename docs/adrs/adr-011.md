# Move FitPro to the team domain fitpro-app.tech
Date: 2026-11-10

## Status
Accepted. Supersedes the hostname in [ADR-004](adr-004.md); the rest of ADR-004 (DNS only in Cloudflare,
Google-managed certificate through Certificate Manager) still applies.

## Decision
Serve FitPro at the apex of the team's domain, `fitpro-app.tech`, which is registered and hosted in Cloudflare. As with
ADR-004, the A record is DNS only (gray cloud) and points at the reserved static IP `fitpro-lb-ip`, and TLS comes from a
Google-managed certificate issued with DNS authorization and served through the existing certificate map
`fitpro-certmap`.

The move happens in two steps so there is no downtime:

1. **Serve both hostnames.** Add `fitpro-app.tech` to `app_hostnames` in Terraform (a new DNS authorization,
   certificate, and certificate map entry; the old ones are untouched), and to `ALLOWED_HOSTS`,
   `CSRF_TRUSTED_ORIGINS`, and both HTTPRoutes in the prod overlay. The new hostname is listed first because
   `scripts/deploy.sh` smoke-tests the first HTTPRoute hostname.
   The same change switches Spotify on in production: the SecretProviderClass mounts the Spotify client secret and
   token encryption key, and the ConfigMap sets `SPOTIFY_CLIENT_ID` and
   `SPOTIFY_REDIRECT_URI=https://fitpro-app.tech/auth-callback/spotify`.
2. **Retire the old hostname** in a later change: redirect `fitpro.rockymountaintechlab.com` to the new domain (or
   remove it), then take it out of `app_hostnames` and the overlay and delete its Cloudflare records.

Order of operations for step 1, since merging to `main` deploys and a failed smoke test rolls the release back:

1. `terraform apply` with both hostnames, then add the `_acme-challenge` CNAME from `dns_authorization_records`.
2. Wait for `gcloud certificate-manager certificates describe fitpro-cert-fitpro-app-tech --location=global` to show
   `ACTIVE`.
3. Add the A record for `fitpro-app.tech` pointing at `lb_ip_address`, DNS only. Until the deploy, the load balancer
   answers 404 for it because no route matches.
4. Add the Spotify client secret's value (`gcloud secrets versions add fitpro-spotify-client-secret --data-file=-`)
   and register `https://fitpro-app.tech/auth-callback/spotify` in the Spotify developer dashboard. A mounted secret
   with no version stops the pods and the migrate Job from starting.
5. Merge the overlay change and let the deploy pipeline run its smoke test against `https://fitpro-app.tech`.

## What this offers
* A team-owned domain: DNS changes no longer depend on one teammate's personal domain, which was ADR-004's main
  limitation.
* No new components or cost beyond the domain itself: the static IP, load balancer, certificate map, SSL policy,
  cluster, and database are unchanged, and Certificate Manager stays within its free tier.
* No downtime: the certificate is issued before any traffic moves, and both hostnames work during the switch.

## Tradeoffs considered
* Host the new domain's DNS at a different provider: ADR-004 expected the DNS to live at the registrar. The domain was
  bought through Cloudflare, so DNS stays there, and the team already knows the DNS-only setup. No change in practice.
* Cut over in one step (swap the hostname everywhere at once): simpler, but the old URL would break immediately and
  the new certificate might not be active at deploy time. Rejected.
* Serve the app on `www.fitpro-app.tech` instead of the apex: Cloudflare allows an A record at the apex, so there is no
  need for a `www` host. A `www` redirect can be added later by adding it to `app_hostnames` and the routes.
* Sessions and cookies: cookies are scoped to the host (`SESSION_COOKIE_DOMAIN` stays unset), so users are logged out
  once when they move to the new domain. Accepted.
* Spotify: the app sends a single `SPOTIFY_REDIRECT_URI`, so Spotify is enabled in production with the new hostname
  only. Linking or signing in with Spotify from the old hostname would return to `fitpro-app.tech`, where the OAuth
  `state` stored in the old host's session isn't present, and fail. Since Spotify was never live on the old hostname,
  no user loses anything; the redirect in step 2 removes the case entirely.
* HSTS: `security.W004` is silenced until the permanent domain is in place. Enabling `SECURE_HSTS_SECONDS` is a
  security posture change with lasting browser effects, so it gets its own change and ADR after the old hostname is
  retired.

> **Update 2026-11-11:** Step 2 is done with a redirect in the Gateway: the `fitpro-old-host-redirect` HTTPRoute
> (`k8s/app/overlays/prod/old-host-redirect.yaml`) answers `fitpro.rockymountaintechlab.com` on both listeners with a
> 301 to `https://fitpro-app.tech`, keeping the path and query. The old host is no longer in the app routes,
> `ALLOWED_HOSTS`, or `CSRF_TRUSTED_ORIGINS`, so those requests never reach Django, and Spotify sign-in can no longer
> start from the old host. A Cloudflare redirect rule was tried first and rejected: Cloudflare only applies rules to
> proxied records, and proxying the old host would reverse ADR-004's DNS-only decision for config that lives outside the
> repo. The old hostname stays in `app_hostnames` (and its A record stays DNS only) because HTTPS requests to it need
> its certificate before the redirect can be sent. To remove it completely later: delete the route from the overlay and
> from the cluster by hand (the CI role can't delete HTTPRoutes), then remove the hostname from `app_hostnames` and its
> Cloudflare records. The text above is kept as the original decision record.
