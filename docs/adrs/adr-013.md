# Rotate the weekly workout split and let users switch it
Date: 2026-11-12

## Status
Accepted

## Decision
The weekly plan from [ADR-012](adr-012.md) no longer repeats the same routine every week. Each new week's plan uses the
next **split style** in rotation, and users can pick a different style or ask for the next one during the week.

| Part | Where | What it does |
| --- | --- | --- |
| Split styles | `plans.generator.SPLIT_STYLES` | `full_body`, `upper_lower`, and `push_pull_legs`, each mapping a number of training days to that week's workouts. Every style that offers a day count trains on the same weekdays, so changing style never changes how many days a user trains, and so never changes their macro targets (they depend on training days). Full body is only offered at 3 days, because with 4 or 5 training days some full-body days would fall back to back |
| Plan data | `WeeklyPlan.data` (JSON) | Gains `split` (the style used) and, once the user has switched, `switches` (a count). No migration. Plans saved before this change have no `split`; `split_of()` infers it from their number of training days, which is how they were built |
| Weekly rotation | `plans.services.get_weekly_plan` | The first visit of a week passes the user's most recent earlier plan's style to `generate_plan(after=...)`, which returns the next style available for the user's training days. A user with no history gets the same default style as before. A skipped week is ignored: rotation continues from the latest plan |
| Switching | `plans.services.switch_split`, `POST /plans/this-week/split/` (`change_split`) | Choose a style, or `next` ("Switch it up"). The workouts are rebuilt in the new style but the saved **macro targets are kept**, so the meal plan stays valid (ADR-012 says a profile change applies from next week). Each swap of an existing plan uses one of `MAX_SPLIT_SWITCHES` (3) per week; choosing a style before the week's plan exists just creates the plan and uses none. The plan row is locked (`select_for_update`) so simultaneous requests can't get past the limit |
| Validation | `plans.forms.SplitChoiceForm` | The posted value must be a known style or `next`; whether it fits the user's training days is checked in the service, and a style that doesn't fit is refused |

## What this offers
* **Variety without planning:** the routine changes every week on its own, and users who want something else can
  choose it.
* **Stable nutrition:** switching split changes exercises, not macro targets or the meal plan.
* **A bounded action:** the weekly limit stops a user from regenerating endlessly, and is the same cap the planned AI
  trainer will sit behind.
* **No schema change:** new styles or exercises are code, not migrations, and old plans still render.

## Tradeoffs considered
* **A `split` and `switches` column on `WeeklyPlan`:** easier to query, but a migration on an existing table for two
  values nothing queries yet. Kept in the JSON; revisit if a feature needs to query them.
* **Random variety instead of rotation:** more surprising, but two weeks in a row could repeat, and tests and users
  can't predict it. Rotation never repeats the previous style.
* **Recomputing macros on a switch:** the number of training days is the same in every style, so they would come out
  equal anyway, but only if the profile hasn't changed. Keeping the saved targets guarantees the meal plan isn't
  remade mid-week.
* **Rate limiting with `accounts.throttle`:** that guards login and sign-up against guessing. The weekly counter is
  the product rule here and the action is a cheap database write; the AI step (below) adds a request throttle.

## Known limitations
* If a user's experience level changes mid-week, a switch rebuilds the workouts for the new level's day count while
  keeping the old macros; a style that doesn't fit is refused. The next week's plan is fully consistent.
* Full body is offered only to 3-day (beginner) plans.
* AI-built plans are not part of this decision. They need their own ADR (new external service and secret).
