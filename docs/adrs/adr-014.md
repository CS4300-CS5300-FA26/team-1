# Start a searched Spotify playlist when a workout starts
Date: 2026-11-17

## Status
Proposed

## Decision
When a user starts today's workout, FitPro searches Spotify for a public playlist that matches the workout and plays it
on the user's active Spotify device. The workout starts whatever Spotify answers.

| Part | Where | What it does |
| --- | --- | --- |
| Start a workout | `POST /plans/workout/start/` (`start_workout`) | Login and CSRF protected. Finds today's day in the weekly plan (rest days start nothing), asks the Spotify service for music, keeps the result in the session with today's date, and redirects to the workout screen, so a reload never starts the music twice |
| Workout screen | `GET /plans/workout/` (`workout`) | Today's exercises, a "Start today's workout" button, and once started, one of three music states: **playing** ("Now playing on Spotify: <name>"), **not linked** (a "Link Spotify for music" button that starts the existing link flow), or **can't play** (the reason and an "Open in Spotify" link to the playlist) |
| Search | `spotify.client.search_playlist` | `GET /v1/search?type=playlist&limit=5` with the workout name minus its A/B variant ("Upper Body A" becomes "upper body workout"). The first entry with a valid base-62 id and a name wins; null or malformed entries are skipped |
| Playback | `spotify.client.start_playback` | `PUT /v1/me/player/play` with `{"context_uri": "spotify:playlist:<id>"}` on the active device. Spotify's error `reason` (`NO_ACTIVE_DEVICE`, `PREMIUM_REQUIRED`) is kept on `SpotifyError.reason` and turned into a message |
| Rules | `spotify.services.start_workout_music` | Not linked: no Spotify call. Revoked access: "link again". Search failure or no result: can't play, no link. Playback failure: can't play, with the playlist link. If Spotify rejects a token we thought was fresh (HTTP 401), the cached token is dropped, refreshed, and the call retried once; a second 401 (or a revoked refresh token) asks the user to link Spotify again, and the rejected token is never reused. Returns a `WorkoutMusic` value that never holds a token |
| Rate limit | `accounts.throttle.acquire_spotify_playback`, `AUTH_THROTTLE['spotify_playback']` | 10 starts per user per 5 minutes. Over the limit the workout still starts and the music says why it didn't |

No new scopes, settings, dependencies, or migrations: ADR-010 already requested `user-modify-playback-state`, and the
result lives in the session.

## What this offers
* **The user story's three scenarios** with no extra steps for the user: one button starts both the workout and the
  music.
* **A workout that never depends on Spotify.** Every Spotify failure becomes a message and, where a playlist was
  found, a link the user can open themselves.
* **Two Spotify calls per start** (search, play), plus a token refresh at most, under a per-user limit, which matters
  with Development Mode's shared quota.
* **Safe output.** The "Open in Spotify" link is built from a validated id, never from a URL Spotify sent, so a bad
  response can't inject a `javascript:` link. Playlist names are autoescaped.

## Tradeoffs considered
* **Build a new private playlist from track search:** closer to the "curated playlist" requirement, but it adds
  several calls per workout, writes playlists into the user's account, and Spotify removed Recommendations for new apps
  in November 2024, so "curated" would still be keyword search. Kept as a follow-up.
* **Pick a device from `GET /v1/me/player/devices`:** could wake an idle device, but costs a third call and could
  start music on a device the user isn't near. Playing on the active device, and asking the user to open Spotify
  otherwise, is what the story asks.
* **Start playback from the browser with the Web Playback SDK:** plays in the FitPro tab, but needs Premium anyway,
  a client-side token, and JavaScript, which the site must work without.
* **A `WorkoutSession` model:** would record workouts, but the story doesn't need history. The session holds today's
  music result; recording workouts can add a model later.

## Known limitations
* **Premium only:** Spotify only allows playback control for Premium accounts; free accounts always get the "Open in
  Spotify" link.
* **Development Mode:** only the 5 allowlisted Spotify users can use it, and the app owner must keep Premium.
* **Search quality:** the first search result is used as is. It may be a Spotify-owned playlist, which new apps can't
  read through the API; playing it by URI isn't documented as restricted, but this hasn't been checked against a real
  account yet.
* **Time zone:** "today" uses the server's time zone (UTC), like the rest of the weekly plan.
