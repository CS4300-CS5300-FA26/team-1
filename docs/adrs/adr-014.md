# Let an AI trainer choose the exercises in the weekly plan
Date: 2026-11-15

## Status
Accepted

## Decision
When it is switched on, the weekly plan from [ADR-012](adr-012.md) and [ADR-013](adr-013.md) gets its exercises from
OpenAI. The rule-based generator still builds the plan first; the AI only replaces the exercises in each training day.

| Part | Where | What it does |
| --- | --- | --- |
| What the AI decides | `plans.ai_trainer.improve_plan` | Which exercises each training day has, their order, and their sets and reps. It does **not** decide the split, which days are training days, the workout names, or the macro targets, so the meal plan and the rotation in ADR-013 keep working |
| The call | `plans.ai_trainer.call_openai` | One HTTPS request to OpenAI's Chat Completions API using Structured Outputs (`response_format` of type `json_schema`, `strict`), with the standard library's `urllib` like the Spotify client. No SDK and no new dependency. A 15 second timeout and no retries |
| What it is told | `plans.ai_trainer.build_request` | The goal, experience level, split name, each day's workout name and the movements it must cover, the exercises the user's equipment allows (names from `plans.generator.EXERCISES`), and the names used last week so it can vary the week. No name, email, user id, weight, height, or other free text |
| Checking the answer | `plans.ai_trainer.validate_days` | Exactly the expected JSON shape; the right number of days; every exercise is in the library, allowed by the user's equipment, and not repeated within a day; every movement the rule-based day covers is still covered; sets 1 to 5; reps in a known format with sane numbers. Any failure throws the whole answer away |
| Falling back | `plans.ai_trainer.improve_plan` | If the AI is off, rate limited, unreachable, slow, refuses, or fails the checks, the rule-based plan is used unchanged (never the starter plan). `improve_plan` never raises. AI-built plans are saved with `"source": "ai"` in the plan JSON, so there is no migration, and the This Week page says when the AI chose the exercises |
| Rate limit | `accounts.throttle.acquire_ai_trainer`, `AUTH_THROTTLE['ai_trainer']` | 10 calls per user per hour, counted before the call. The app also limits a user to one call when a week's plan is created plus the switches allowed by ADR-013 |
| The key | `OPENAI_API_KEY` in `fitpro/settings.py` | Read with `read_secret('openai-api-key', 'OPENAI_API_KEY')`: `.env` locally, `/var/secrets/openai-api-key` in Kubernetes. It is read only inside `call_openai`, sent only in the `Authorization` header, and never put in a template, a response, a log line, or an error message. Empty switches the AI trainer off. The setting is forced empty while tests run (`TESTING`), so tests and scenarios can't call OpenAI |
| The model | `OPENAI_MODEL`, `OPENAI_REASONING_EFFORT` | Settings, so they can change without a code change. The default model is `gpt-6-luna`, the one the team's key can use; it is a reasoning model, so `reasoning_effort` defaults to `low` to keep the wait short, and the output limit leaves room for its thinking (reasoning tokens count against it). Leave the effort empty for a model that doesn't take it |

## What this offers
* **Fresh workouts:** the AI varies the choice and order of exercises week to week, avoiding last week's where an equally
  suitable alternative exists.
* **A safe boundary:** the AI can only pick from our own library, for the user's own equipment, so it can't invent an
  exercise, suggest equipment the user doesn't have, or touch macros and the meal plan.
* **It keeps working without the AI:** no key, no network, an invalid answer, or the rate limit all end in the
  rule-based plan from ADR-013.
* **No personal data leaves the app:** only the goal, experience level, and exercise names are sent.

## Tradeoffs considered
* **Let the AI design the whole plan, including the split and the macros:** more flexible, but the days per week feed the
  macro targets and meal plan, and free-form output is hard to validate. Rejected; the AI fills in a plan whose shape
  we already trust.
* **The `openai` SDK:** convenient, but AGENTS.md says not to add a dependency when the standard library covers the need,
  and one POST with `urllib` is what Spotify already does. Revisit if we need streaming or several endpoints.
* **Free-text coaching notes from the AI:** would show unvalidated model text to users. Left out on purpose.
* **Retrying a failed call:** doubles the cost and the wait for a user who is already waiting. We fall back instead.
* **Running the call in a background job:** the page wouldn't wait, but it needs a queue and worker, which is new
  infrastructure. The call is synchronous with a short timeout; revisit if the wait is a problem.
* **A validation library such as pydantic:** the checks are short, explicit, and tested, so no new dependency.
* **Logging error bodies from OpenAI to help debugging:** OpenAI's authentication errors can echo part of the key, so only
  the HTTP status or the kind of failure is logged.

## Known limitations
* The exercise library is small, so the AI often chooses between only one to three alternatives for a movement. Variety
  grows as the library grows (the exercise demo feature will add to it).
* The first visit of a week, and a split switch, can wait up to 15 seconds for OpenAI before falling back.
* The production secret is not set up. It needs a Secret Manager secret in `terraform_scripts/secrets.tf` and a mount in
  `k8s/app/base/secretproviderclass.yaml` (path `openai-api-key`), which is an infrastructure change for the team to make
  and review. Until then production has no key and uses the rule-based plan.
* OpenAI processes the request, so the data sent (goal, experience level, equipment-based exercise list) is subject to
  OpenAI's terms; no personal identifiers are included.
