# Store each week's workout plan as JSON and give its macro targets to the meal plan
Date: 2026-11-10

## Status
Accepted

## Decision
The `plans` app generates a weekly workout plan with daily macro targets from the onboarding profile, stores it, and
connects those targets to the meal plan (D-4, through the connector from [ADR-008](adr-008.md)).

| Part | Where | What it does |
| --- | --- | --- |
| Generator | `plans/generator.py` | Pure rules, no database: the training split from experience level (3, 4, or 5 days), exercises picked by the user's equipment with a bodyweight fallback for every movement, sets and reps by goal, and daily calories, protein, carbs, and fat from a Mifflin-St Jeor estimate adjusted for goal and training days |
| Storage | `plans.models.WeeklyPlan` | One row per user per week: `user`, `week_start` (the Monday), and the generated plan in a `JSONField` (`days` and `macros`, shape documented in `generator.py`). A database `UniqueConstraint` on (`user`, `week_start`) enforces one plan per week; the first visit creates it with `get_or_create`, so two simultaneous first visits can't create two rows |
| Fallback | `plans/starter.py` | A fixed 3-day bodyweight plan with general targets, shown (and never saved) when generation fails, so the next visit tries again |
| Pages | `/plans/this-week/` (`this_week`), `/plans/nutrition/` (`nutrition`) | Login required; users who haven't finished onboarding are sent there. Each reads only the signed-in user's own plan |
| Meal plan connector | `plans.macro_targets.PlanMacroTargets`, wired as `NUTRITION_MACRO_TARGETS_PROVIDER` | Returns the plan's daily target for all seven days, Monday first, so `/meal-plan/` aims at the numbers the Nutrition page shows. It only reads the week's **saved** plan, because the meal plan calls connectors on every page view and they must not have side effects. With no saved plan this week (the user hasn't opened This Week or Nutrition yet, hasn't onboarded, or generation failed and the unsaved starter plan was shown), it returns `None`, D-4's "No plan yet", and the meal plan uses the FDA Daily Values. Once the first visit saves the plan, the meal plan's stored week is remade for the new targets (ADR-008) |

## What this offers
* **A stable week:** the plan and its targets don't change under the user mid-week, and the meal plan's stored week is
  only remade when the targets it was built for change (ADR-008).
* **One source of truth for targets:** the This Week, Nutrition, and Meal Plan pages all show or use the same daily
  protein, carbs, and fat, and `nutrition` still never imports `plans` (it knows the connector only by its dotted path).
* **A schema that doesn't follow the exercise library:** adding or renaming exercises, splits, or plan fields needs no
  migration, and old weeks still render as they were generated.
* **Integrity in the database:** one plan per user per week is a constraint, not just a check in code.

## Tradeoffs considered
* **Normalized tables (plan, day, exercise rows):** queryable per exercise, but three tables and a migration for every
  change to the plan's shape, and nothing reads individual exercises yet. Rejected for now; the JSON can be migrated
  into tables if a feature needs to query it (D-3's exercise tracking may).
* **Generate on every request, store nothing:** no table, but the plan would change whenever the profile or the rules
  change, including mid-week, and the meal plan's targets with it. Rejected.
* **Let the connector call `get_weekly_plan`:** opening the Meal Plan page would then create a workout plan row as a
  side effect, against ADR-008's connector rules. Rejected.
* **Calculate the targets from the profile when there is no saved plan:** read-only and gives the same numbers, but
  it breaks the D-4 contract ("return None when the user has no plan yet") and would show personal targets for a plan
  the user has never seen. Rejected in review; the meal plan keeps its labelled Daily Values fallback until the plan
  exists.
* **Lower carbs on rest days:** ADR-008's connector allows a different target per day. The plan has one daily target,
  and the Nutrition page says it stays the same on training and rest days, so the meal plan gets the same target all
  week. Per-day targets would change the plan's data shape, both pages, and the connector together.
* **Pass the starter plan's targets to the meal plan:** they aren't personal, so the meal plan's own published
  fallback (the FDA Daily Values) is the more honest choice and is already labelled on that page.

## Known limitations
* Until the user opens This Week or Nutrition in a given week, the meal plan uses the Daily Values and says so; the
  first visit switches it to personal targets and remakes that week's meal plan.
* Onboarding doesn't ask for age or sex, so the estimate uses age 25 and the midpoint of Mifflin-St Jeor's male and
  female constants. Targets are estimates, not medical advice, and the pages say so.
* A profile change applies from the next week's plan. Until then the week's saved plan, and so the meal plan, keep the
  targets it was generated with.
* The stored JSON isn't validated against a schema on read. Only the generator writes it, and the connector ignores
  (and logs) targets the meal plan can't use.
