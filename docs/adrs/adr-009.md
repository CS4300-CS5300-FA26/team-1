# Build workout plans and exercise tracking on a text-only exercise catalog
Date: 2026-11-02

## Status
Proposed

## Decision
Story D-3 (workout split generation) and exercise tracking live in a new `workouts` app. It connects to the meal plan the way [ADR-008](adr-008.md) describes: `NUTRITION_WORKOUTS_LINK` now points at its This Week page, and `workouts.services.training_days(user, week_start)` is there for D-4 (rest days vs training days). `nutrition` does not import `workouts`.

| Part | Where | What it does |
| --- | --- | --- |
| Exercise catalog | `workouts/data/exercise_catalog.json`, `Exercise` | 1,324 exercises: name, body part, target and secondary muscles, equipment, and English step-by-step instructions. **No images or video.** Built from the upstream `exercises.json` by `manage.py build_exercise_catalog` |
| Licence notice | `workouts/data/LICENSE-exercise-data.txt`, the catalog's `notice` field | The dataset's MIT licence travels with the data, as it requires |
| Loading | `catalog_loader.py`, `apps.py`, `manage.py load_exercise_catalog` | The same pattern as the recipe catalog: validated row by row, one transaction, idempotent, run after every `migrate`. An exercise that leaves the file is marked `is_active=False`, never deleted, because logged sets point at it |
| Equipment classes | `domain.EQUIPMENT_CLASS` | Maps the dataset's 28 equipment names to the six onboarding choices. Equipment onboarding can't ask about (kettlebell, stability ball, weighted, ...) is `other` and is never planned |
| Exercise pools | `foundation.py` | About 130 standard movements picked by hand, per movement slot and equipment class, by catalog id |
| Planner | `planner.py` (pure: no database, no clock, no randomness) | See "Planning rules" |
| Stored weekly plan | `WorkoutPlan`, `PlannedWorkout`, `PlannedExercise` | One plan per user per Monday, made the first time This Week is opened and reused all week. Remade when its inputs change (goal, experience, equipment, training days, `PLANNER_VERSION`) or when one of its exercises was retired from the catalog |
| Training days | `WorkoutPreference` | The user's 3, 4, or 5 days a week. Kept in the `workouts` app so `core.UserProfile` (an existing table) is not changed. Until chosen: 3 for beginners, 4 for intermediate, 5 for advanced |
| Tracking | `WorkoutSession`, `LoggedSet` | One session per planned workout (a database constraint, so a double click can't make two). Sets store reps and weight, or minutes for cardio. A session keeps its title and sets after its plan is replaced |
| Pages | `/workouts/`, `/workouts/session/<id>/`, `/workouts/history/` | The week with a Start button per day; a workout page with how-to steps, a row per set (weights start from the last time), save or finish, and a rest timer (`rest_timer.js`, progressive enhancement); weekly consistency and volume with recent workouts |

**Planning rules.**
* **Split:** 3 days is full body A/B/C (Mon, Wed, Fri); 4 is upper/lower twice (Mon, Tue, Thu, Fri); 5 is push, pull, legs, upper, lower (Mon-Fri).
* **Exercises:** only from `foundation.POOLS`, for the equipment the user has. Bodyweight moves fill in only where that equipment has no option for a movement (core work for a dumbbell user), so someone who owns dumbbells isn't given bodyweight squats. A movement with nothing for their equipment is left out (a pulldown with bodyweight only) rather than swapped for a poor fit; a session left under four exercises is topped up with other movements.
* **Rotation:** each time a movement appears in the week the planner takes the next exercise in its list, and the seed shifts where the list starts. "Generate a new workout plan" bumps the seed.
* **Sets and reps:** by goal and experience. Build muscle is 6-10 reps on big lifts with 2 minutes rest; fat loss 10-15 with 1 minute; maintain 8-12; endurance 15-20. Beginners never get fewer than 8 reps. Fat loss and endurance end each session with 10-20 minutes of cardio.

**Data privacy.** Every view is `login_required` and looks rows up through the signed-in user (`plan__user`, `user`), so another user's workout or session is a 404, never an error that confirms it exists. Logged-in tests prove it for start, view, save, and history. State changes are `POST` with CSRF. Posted field names are built from the form's own rows, so values for rows that aren't in the workout are ignored. Reps, weight, and minutes are bounded in the form and by database `CHECK` constraints.

## What this offers
* A working D-3 and tracking feature with no new dependency, service, paid API, or datastore, and nothing that calls the network, so workouts keep working when anything external is down (requirement 5.5.3).
* The planner's output is plain structured data in the same shape an AI generator would need to produce. If the team adds the OpenAI-based agent from the requirements later, it can sit behind the same `plan_week` signature, with its output validated against the same models and constraints (requirement 5.5.4). It was not built now: it needs a paid API, secrets, and failure handling, and the rules above already give a safe plan.
* The repository stays small. The upstream file is 17.4 MB because every instruction is repeated in ten languages; the catalog is 0.97 MB.

## Tradeoffs considered
* **Media and licence.** The dataset's MIT grant covers the code, data structure, and instruction text. The images and videos are Gym visual's, used by the dataset author with permission, and are *not* licensed to us. FitPro uses neither, and `build_exercise_catalog` drops every media field (`image`, `gif_url`, `media_id`, `attribution`), with a test that fails if one comes back. The upstream `image` fields are Gym visual media too, not only the videos. Using any of it would need FitPro's own licence from Gym visual, blob storage ([requirements 5.2](../original_customer_requirements.md)), and a new ADR.
* **English only.** The ten-language text is why the file was large. Dropping nine languages loses nothing the app uses today. `build_exercise_catalog` can be changed to keep them if translation becomes a goal.
* **Hand-picked pools vs choosing by dataset labels.** The dataset has no difficulty rating, and its `target` labels are loose: stretches and "flutter kicks" are filed under glutes, and plain squats under glutes rather than quads. Choosing by label would put odd or advanced moves in a beginner's week. The cost is a list to maintain; a test checks every id exists, is active, and is listed under the right equipment. **The picks and the sets, reps, and rest rules are our judgment, not a trainer's, and should be reviewed by someone qualified before real users rely on them.**
* **Exercises in the database vs reading the JSON at runtime.** Logged sets and plans need foreign keys, and loading after `migrate` is already how recipes work. The cost is 1,324 rows rewritten on each `migrate` (well under a second).
* **Retire, don't delete.** Deleting an exercise would fail on its logged sets or erase history. Retired exercises stay in old history and are replaced in current plans.
* **Days per week in its own table.** Adding it to onboarding would change `core.UserProfile` and the questionnaire for a setting most users won't touch. A user who wants a different number changes it on This Week.
* **No rate limit on the new endpoints.** They don't authenticate, send email, or call anything external, and making a plan takes milliseconds of CPU. If the planner ever calls an AI service, that endpoint needs one (reuse `accounts/throttle.py`).

## Known limitations
* The requirement that the agent "refines future splits" from logged results is not built. Logging only prefills the last weight used. Progression (adding weight or reps) is a follow-up.
* No swapping an exercise for another, and no browsing the full catalog. The page links nothing to the 1,200+ exercises outside the pools, though they can be logged if a later plan uses them.
* Some bodyweight moves need something to hold on to (an inverted row needs a sturdy table or bar); the how-to steps say so, but onboarding doesn't ask.
* "Today" and the week boundary use the server's time zone (UTC), as the meal plan does.
* `LoggedSet` keys a set by exercise and set number, so a workout can't use the same exercise twice. The planner never does that.
* The 15-20 rep endurance rule applies to every compound lift, including deadlifts and squats. It is a conservative way to keep loads moderate, and the first thing a trainer may want to change.
