# Build the grocery list from the stored meal plan, with prices from a reviewed file of cited quotes
Date: 2026-11-03

## Status
In Review

## Decision
Story D-6 (grocery list generation, issue #11) lives in its own `grocery` app. It plugs into the meal plan the way
[ADR-008](adr-008.md) designed: it **reads** the week's plan through `nutrition.services.stored_week_plan` and
**supplies** prices by implementing the `NUTRITION_GROCERY_PRICE_SOURCE` connector. The meal plan code did not change.

| Part | Where | What it does |
| --- | --- | --- |
| Grocery List page | `/grocery-list/` (`grocery.views`, `grocery/grocery_list.html`) | Login required, onboarded users only. Shows this week's ingredients combined, each with the amount to buy and an estimated cost, an estimated total, an over-budget notice, a "How this list was made" note, and a pantry section. With no meal plan this week it shows a prompt and a button to create one (the "Empty week" scenario); it never creates a plan |
| Combining and amounts | `grocery/lists.py` (pure, no I/O) | Adds up every weighed line of every planned meal by `line.ingredient.key`, so rice on Monday and on Wednesday is one row. Each total is shown the way a shopper says it: **cups, tbsp, or tsp** for ingredients with a density, a **count** for ingredients with a weight each (rounded up), and **oz or lb** for the rest. Amounts are rounded to quarters (halves for tablespoons and ounces) and never to zero |
| Costs | `grocery/lists.py`, `grocery/services.py` | Prices come from the connector, averaged per ingredient by `nutrition.pricing` exactly as the meal plan does. Each item is costed in **whole packages**, and the total is `nutrition.domain.purchase_cost`, the same function the meal plan uses, so the two pages show the same estimate |
| Price source | `grocery/prices.py`, `grocery/data/price_quotes.json` | `StoredGroceryPrices` returns the quotes in a reviewed JSON file. Every quote has a price, a quantity and unit, a source, and the date it was observed, and the file is validated when read. `NUTRITION_GROCERY_PRICE_SOURCE` now names it |
| Tests | `grocery/test_*.py`, `grocery/testing.py`, `features/grocery_list.feature` | Unit tests for amounts and costs, page tests (access, empty week, only your own plan, fallbacks, agreement with the meal plan), tests that the price file is valid and prices real catalog ingredients, and the two issue scenarios plus a missing-prices fallback |

**Rounding rule (the AGENTS.md note about D-6 totals).** The total is the sum of unrounded whole-package costs,
rounded to the cent once, because that is how the meal plan computes its estimate and the two must agree. Each row's
cost is rounded to the cent on its own, so the rows can differ from the total by a cent or two. The page says so.

**Missing prices.** An ingredient with no quote has no price, and nothing is guessed. If every ingredient is priced
the page shows "Est. $X". If only some are, it shows each known cost, a "Total of priced ingredients", and a note
that there is no total yet. If none are, it shows the list with no costs.

### The price data, and what is not done yet
**9 of the catalog's 55 ingredients**: white rice, dry pasta, eggs, whole milk, cheddar cheese, bananas, potatoes, tomatoes, and chicken breast come from BLS. ([Average Retail Food and Energy Prices](https://www.bls.gov/regions/mid-atlantic/data/averageretailfoodandenergyprices_usandNortheast_table.htm)), BLS does not publish most of the others (canned beans, oats, tofu, frozen vegetables, and so on).
The rest of the quotes are from Walmart. Together, they cover 54 out of 55 ingredients.

* **Most recipes are fully priced** so the meal plan shows the prices.
  whole-package costing rounds up to that unit. Real packages are bigger (a 5 lb bag of rice), so these quotes can
  understate a week's cost a little. "Tomatoes" uses BLS's field-grown fresh price, and "chicken breast" its
  boneless price.

### Safe by default
* The page requires login, reads only `request.user`'s plan, takes no query-string or form input, and has no write
  action, so there is no CSRF or injection surface of its own. A test proves another user's plan is never shown.
* A price source that raises is caught and logged, and the list still shows (a test covers it).
* Nothing calls the network at runtime and no key or secret is needed. Prices change only through a reviewed PR.
* No rate limit: the page is a cheap read of local data, like the meal plan page. If the price source ever calls a
  network service, it needs one (see AGENTS.md).

## What this offers
* **No made-up numbers.** Every price has a source and a date, and a missing price is shown as missing.
* **One answer.** The list and the meal plan share the same prices and the same costing function, and a test checks
  that their totals match.
* **Independent work.** D-6 changed one setting and added an app; the meal plan, its planner, and its page were not
  edited (only three of D-5's tests were pinned to the "not connected" default, as AGENTS.md instructs).
* **Easy to extend.** Adding a price is one JSON entry, and the tests check its key, unit, source, and date.

## Tradeoffs considered
* **A recipe or price API (Spoonacular):** rejected in ADR-008 (50 points a day on the free plan, terms that allow
  caching for only an hour, and a key to manage), and the customer confirmed it isn't required. The price source is
  still a connector, so a live source can replace the file later.
* **A store API (for example a grocery chain's product search):** it would give real shelf prices, but needs an
  approved developer account, a secret, network calls on every page view, and rate limiting. Out of scope for this
  sprint; the connector allows it later.
* **Estimating the missing prices (BLS averages scaled to similar foods, or guesses):** rejected. ADR-008 forbids
  invented numbers, and a wrong cost would mislead a budget-conscious user.
* **Prices in the database (a model, admin-editable):** rejected. The admin site is disabled (ADR-007), a file in the
  repo is reviewed in a PR with its source, and a migration would not buy anything yet.
* **Prices in the recipe catalog:** rejected in ADR-008 (prices belong to D-6).
* **A "got it" checkbox per item:** needs stored state or JavaScript for a feature the story doesn't ask for. A
  follow-up.
* **Showing grams only:** accurate, but nobody shops in grams. Cups, counts, and pounds come first, with the grams
  shown next to them so the numbers can be checked.

**Known limitations and follow-ups:**
* Cups, tablespoons and teaspoons are US customary, and amounts are rounded, so they are for shopping, not recipes.
* The list shows what the plan uses, not what a package holds; leftover quantity isn't tracked.
* If the recipe source is unavailable, the stored plan can't be read and the page asks the user to make a meal plan,
  which then explains the outage.
* Wiring the other connectors (D-3, D-4) is unchanged; see the temporary note in AGENTS.md.
