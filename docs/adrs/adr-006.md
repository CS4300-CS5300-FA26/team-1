# Rate limit login and registration, and pin Django's recommended security settings
Date: 2026-10-29

## Status
Accepted. Builds on [ADR-005](adr-005.md), whose "no rate limiting" known gap this closes.

## Decision
Login and registration are rate limited by a small database-backed throttle (`accounts/throttle.py`, model `accounts.ThrottleEvent`), with no new dependency. Blocked requests get HTTP 429 with a `Retry-After` header and a generic "Too many attempts" message. Limits live in `settings.AUTH_THROTTLE`:

| Counter | Counts | Limit | Window |
| --- | --- | --- | --- |
| `login-id` | Failed logins for one typed identifier from one IP | 5 | 15 min |
| `login-ip` | Failed logins from one IP, any identifier | 20 | 15 min |
| `register-ip` | Registration POSTs from one IP | 10 | 1 hour |

* The check runs in `CustomLoginView.post()` before `authenticate()`, so a locked-out client cannot keep guessing, even with the right password. Failures are recorded in `form_invalid()`. A successful login clears that identifier's counter.
* Identifiers are lowercased and stripped before counting, then stored only as a SHA-256 hash together with the IP, so the table holds no emails or usernames. Old rows are pruned whenever a new one is written.
* Client IP: behind the GKE load balancer `X-Forwarded-For` ends in `<client>, <balancer>`. When `BEHIND_HTTPS_PROXY` is on we use the second-to-last entry, because anything further left is client-supplied and could be forged to dodge the limit. Otherwise we use `REMOTE_ADDR`.
* Throttled attempts are logged to the `accounts.security` logger (stdout, so Cloud Logging picks them up).

Settings pinned explicitly from Django's [security / deployment checklist](https://docs.djangoproject.com/en/6.1/howto/deployment/checklist/), so a later edit can't loosen them unnoticed: `SECURE_CONTENT_TYPE_NOSNIFF`, `SECURE_REFERRER_POLICY='same-origin'`, `SECURE_CROSS_ORIGIN_OPENER_POLICY='same-origin'`, `X_FRAME_OPTIONS='DENY'`, and `CSRF_COOKIE_SAMESITE='Lax'`. These add to what ADR-005 and the settings already had: `HttpOnly`/`Secure`/`SameSite` session cookies, `Secure` CSRF cookie behind the proxy, session key rotation on login, CSRF on every POST, `sensitive_post_parameters` on registration, a generic login error, safe `next` redirects, and the four password validators.

## What this offers
* Online password guessing and credential stuffing become slow: at most 5 guesses per account per IP per 15 minutes.
* Shared across pods. The Deployment runs 2 replicas and Django's default cache is per-process, so a cache-based limit would silently double.
* No new dependency, and the table is created by the existing migrate Job.
* Keying lockouts on identifier **and** IP means an attacker cannot lock a victim out of their own account from a different address.

## Tradeoffs considered
* **`django-axes`:** more featureful (lockout UI, admin integration, reset commands) but a third-party package to track, and it also hooks the admin login. Rejected for now. Our version is about 70 lines and covered by tests. Axes remains the upgrade path if requirements grow.
* **Django cache (LocMem / Redis):** cheaper per request, but LocMem is per pod and Redis is new infrastructure. The extra DB queries (a few indexed counts per login POST) are acceptable at this scale.
* **Throttling by IP alone:** simpler, but users behind a shared NAT would lock each other out. Combined with the per-identifier key it is fairer; the larger `login-ip` limit still bounds password spraying across many accounts from one address.
* **Known limits:** a botnet using many IPs can still try 5 passwords per IP per account. Strong password validators (ADR-005) are the main defence there. Registration returning "email already exists" still allows email enumeration, though it is now rate limited. `/admin/login/` is not throttled and remains a follow-up (restrict by path or network). We did not enable HSTS or `SECURE_SSL_REDIRECT`, for the reasons in `settings.py`.
* **Ratelimit headers / CAPTCHA:** deferred. Could be added if abuse shows up in the logs.
