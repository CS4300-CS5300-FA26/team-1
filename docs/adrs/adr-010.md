# Use OAuth 2.0 Authorization Code flow (backend-handled) for Spotify integration
Date: 2026-11-09

## Status
Accepted

## Context
Story D-7 (issue #12) adds Spotify account linking and "Log in / Sign up with Spotify". Later features (workout
playlists, playback control) need long-term access to a user's playlists and playback, not just a one-time sign-in.

Spotify implements OAuth 2.0 only: Authorization Code, Authorization Code with PKCE, and Client Credentials (the
Implicit grant is listed as deprecated). It does **not** implement OpenID Connect, so there is no ID token. We have to
establish identity ourselves by calling `GET /v1/me` with the access token and reading the Spotify user id.

## Decision
Use the **Authorization Code flow, performed entirely by the Django backend** (new `spotify` app). The client secret
and every user token stay on the server; the browser only ever sees Spotify's consent page and our redirects.

| Part | Where | What it does |
| --- | --- | --- |
| Start | `POST /spotify/link/`, `/spotify/login/`, `/spotify/signup/` (`spotify.views.start`) | Stores a random 256-bit `state`, the mode (link, login, signup), the user id for a link, and a timestamp in the session, then redirects to `https://accounts.spotify.com/authorize`. POST with a CSRF token, so another site can't start a flow for a user |
| Callback | `GET /auth-callback/spotify` (`spotify.views.callback`) | Pops the stored flow (single use) and compares `state` in constant time; rejects a missing, mismatched, or older-than-10-minutes state before any token request. `error=access_denied` returns to where the user started with "Spotify not connected". Otherwise exchanges the code, calls `GET /v1/me`, and applies the mode's rule below |
| Account | `spotify.models.SpotifyAccount` | One-to-one with `User`; unique `spotify_id`, `display_name`, encrypted `refresh_token` and `access_token`, `expires_at`, granted `scopes`, `needs_relink` |
| Token helper | `spotify.services.get_access_token(user)` | The only way to read an access token. Returns the stored one if it has more than 60 s left; otherwise locks the row (`SELECT ... FOR UPDATE`), re-checks, and refreshes. A new refresh token replaces the stored one only if Spotify returns one. On `invalid_grant` it clears both tokens and sets `needs_relink` |
| Connection test | `GET /spotify/status/` | Login required, rate limited, `Cache-Control: no-store`. Calls `GET /v1/me` through the token helper and returns `{"state", "message", "display_name"}`, never a token. The profile page calls it on load and shows grey (checking), green (OK), or red with troubleshooting steps |
| Unlink | `POST /spotify/disconnect/` | Deletes the link and its tokens. Refused when the user has no usable password, because Spotify is then their only way to log in |

**Mode rules.** Accounts are matched on the Spotify user id from `GET /v1/me` only.

* **link** (logged in): attach to the current user, who must be the same user that started the flow. Rejected if that
  Spotify id is linked to a different user. Relinking the same id refreshes the tokens and clears `needs_relink`.
* **login**: if the Spotify id is linked to an active user, log them in (`login()` rotates the session key). Otherwise
  show "No FitPro account is linked to that Spotify account. Log in with your email and password, then link Spotify
  from your profile." **Email is never used to find an account.**
* **signup**: create a user with an unusable password, a `UserProfile`, and the link, then go to onboarding. Rejected
  with the same guidance if the email from Spotify already belongs to a local account, or if the Spotify id is
  already linked.

**Scopes** (`settings.SPOTIFY_SCOPES`, [scopes reference](https://developer.spotify.com/documentation/web-api/concepts/scopes)):
`user-read-private` and `user-read-email` for identity; `playlist-read-private`, `playlist-modify-private`,
`playlist-modify-public`, `user-read-playback-state`, `user-modify-playback-state`, and `user-read-currently-playing`
for the playlist and playback features that follow. The granted scopes are stored as Spotify returns them.

**Secrets and configuration.** `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFY_REDIRECT_URI`, and
`SPOTIFY_TOKEN_ENCRYPTION_KEY` are read in `settings.py` (`read_secret()` for the three secrets, so Kubernetes can mount
them from Secret Manager). None set: the feature is off and its buttons are hidden. Some but not all set, or a malformed
key: the app refuses to start with an `ImproperlyConfigured` error naming the missing settings (`spotify/config.py`).
The redirect URI must match the Spotify dashboard
[exactly](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri); Spotify rejects `localhost`, so
local development uses `http://127.0.0.1:8000/auth-callback/spotify`.

**Encryption at rest.** Both tokens are stored with Fernet (AES-128-CBC with HMAC-SHA256, from the `cryptography`
package) in a small `EncryptedTextField`. `SPOTIFY_TOKEN_ENCRYPTION_KEY` may list several comma-separated keys
(newest first) so a key can be rotated without losing links. A token no configured key can decrypt is treated as
revoked (`needs_relink`), not as a crash.

**Abuse controls** (reusing `accounts/throttle.py`, [ADR-006](adr-006.md)): starting "Log in / Sign up with Spotify"
is limited to 20 per IP per 15 minutes (`spotify_auth`), and the connection test to 30 per user per 5 minutes
(`spotify_status`), because each check calls Spotify. Linking needs a logged-in user and isn't separately limited.

**Logging.** Events are logged with the FitPro user id only. Tokens, codes, `state`, and response bodies are never
logged; Spotify's error code is logged with non-printable characters stripped. `Tokens.__repr__` hides the tokens.

## Rationale
* Spotify's [authorization guide](https://developer.spotify.com/documentation/web-api/concepts/authorization)
  recommends the Authorization Code flow for long-running applications, such as server-side web apps, that can refresh
  access tokens and can safely store the client secret. FitPro is a server-rendered Django app, so it can.
* The refresh token lets the backend get new access tokens, which
  [last one hour](https://developer.spotify.com/documentation/web-api/tutorials/refreshing-tokens), without
  prompting the user again. Playlist and playback features need that. Spotify doesn't always return a new refresh token
  ("When a refresh token is not returned, continue using the existing token"), so we only replace it when one comes back.
* Tokens and the client secret never reach frontend JavaScript. The profile page's script only sees a state string.
* Flow details follow the [code flow tutorial](https://developer.spotify.com/documentation/web-api/tutorials/code-flow):
  `state` against CSRF on the redirect, and HTTP Basic client authentication on the token endpoint.

## Related decision: link on the Spotify user id, never auto-link on email
Spotify's [Get Current User's Profile](https://developer.spotify.com/documentation/web-api/reference/get-current-users-profile)
says of the `email` field: "This email address is unverified; there is no proof that it actually belongs to the user"
(the field is also marked deprecated). If FitPro linked or logged in by email, anyone could put a FitPro user's address
on their own Spotify account and sign in as that user, a well-known account takeover pattern. So the Spotify id is the
only key, Spotify login never falls back to email, and a Spotify sign-up whose email already exists locally is refused
with instructions to log in with a password and link from the profile. Tests cover both.

## What this offers
* One backend flow serves link, login, and signup, with one callback and one place for the security checks.
* A per-request, single-use, expiring `state` bound to the session; a link can only attach to the user who started it.
* Tokens encrypted at rest, rotatable keys, and a single, row-locked refresh path, so concurrent requests refresh once.
* Revocation is handled: a rejected refresh token clears the tokens and the profile shows "Reconnect Spotify".
* No secrets in the browser, no new infrastructure, and the feature switches off cleanly when not configured (CI and
  the container build run without it).

## Tradeoffs considered
* **Authorization Code with PKCE:** for clients that can't keep a secret (mobile, desktop, browser-only apps). Our
  backend can hold the secret, so PKCE adds nothing the client secret doesn't already provide here.
* **Client Credentials:** authenticates the app, not a user, so it can't read profiles or playlists. Unusable.
* **Implicit grant:** deprecated by Spotify, and it puts the access token in the browser with no refresh token.
* **`django-allauth` / `social-auth-app-django`:** full-featured, but large dependencies whose defaults (for example
  connecting accounts by email) need careful overriding, and they would own login UX the team already built. The whole app
  is about 700 lines including docstrings, and fully tested. Allauth remains an option if more providers are added.
* **`requests` for HTTP:** the standard library's `urllib` covers three calls; AGENTS.md says not to add a dependency
  the standard library covers. A test double replaces `urlopen`, so tests still exercise our request and parsing code.
* **`cryptography` (new dependency):** the standard library has no authenticated symmetric encryption, and encrypting
  tokens at rest is required. `cryptography` is the de facto standard, maintained by the PyCA, and already a common
  transitive dependency. Alternatives such as `django-fernet-fields` are unmaintained wrappers around it.
* **Storing tokens unencrypted, or only in the session:** unencrypted tokens would leak with any database backup or
  dump; session-only tokens disappear at logout, so background playlist features couldn't use them.
* **Showing the connection status server-side only:** it would call Spotify while rendering the profile and slow the
  page. The JSON check keeps the page fast and works without JavaScript (it then reads "Connection not checked yet").

## Consequences and known limitations
* We must manage the encryption key (losing it forces every user to relink) and handle refresh failure and revocation
  (`needs_relink`). Spotify has no token revocation endpoint, so "Disconnect Spotify" deletes our copy and the profile
  links to Spotify's "Manage apps" page for revoking FitPro's access on Spotify's side.
* **Spotify Development Mode** limits the app to [5 authorized users](https://developer.spotify.com/documentation/web-api/concepts/quota-modes),
  each added to the app's allowlist in the Spotify dashboard. Others get an error from Spotify. Going beyond that needs
  Spotify's extended quota review.
* Users who signed up with Spotify have no password and can't unlink until they have one, and FitPro has no
  "set a password" page yet. Follow-up.
* The emails Spotify-created accounts get are unverified, like every FitPro email today (README "Known gaps").
* Production needs the three secrets added to Secret Manager and the SecretProviderClass, and the production redirect
  URI registered with Spotify. Until then the feature stays off in production. Infrastructure changes go through
  Terraform and the infrastructure owner.
