# Build the weekly meal plan as a pure planner behind two swappable ports
Date: 2026-10-29

## Status
Accepted

## Decision
Story D-5 (weekly budget meal plan) lives in a new `nutrition` app, split so that the parts likely to change are
hidden behind small interfaces. This follows the information-hiding and dependency-inversion guidance in
[swebook.org chapter 6](https://www.swebook.org/chapters/06-design-and-architecture/).

| Module | Responsibility (its "secret") |
| --- | --- |
| `nutrition/domain.py` | Immutable value types: `Recipe`, `MacroTargets`, `PlannedDay`, `MealPlan`. No Django imports |
| `nutrition/planner.py` | The planning rules (pure, deterministic, no I/O) |
| `nutrition/ports.py` | The two interfaces the planner needs, `RecipeSource` and `MacroTargetsProvider`, and the loader that picks implementations from settings |
| `nutrition/recipe_sources.py` | Adapters: `StarterCatalogSource` (bundled JSON, no network) and `SpoonacularRecipeSource` |
| `nutrition/macros.py` | `NoMacroTargets`, a placeholder until D-4 |
| `nutrition/services.py` | `weekly_meal_plan(user, budget)`, the one entry point that wires ports to the planner |
| `nutrition/views.py` | `/meal-plan/`: login and onboarding checks, then rendering |

**Plug-in points.** Both are dotted paths in settings, so swapping an implementation changes no planner code:
* `NUTRITION_MACRO_TARGETS_PROVIDER`
  * D-4 (macro generation) adds a class with `weekly_targets(user, week_start) -> 7 MacroTargets | None` (Monday
    first, so rest days can have lower carbs) and points this setting at it.
  * Until then plans are optimised for cost alone, and the page says so.
  * A provider that returns a malformed week is logged and ignored rather than breaking the page.
* `NUTRITION_RECIPE_SOURCE`
  * Chosen with the `RECIPE_SOURCE` environment variable: `catalog` (default) or `spoonacular`, which needs
    `SPOONACULAR_API_KEY` or the `spoonacular-api-key` mounted secret.
  * Every source returns validated `Recipe` objects or raises `RecipeServiceUnavailable`.

**Planning rules.**
* One recipe per day, cooked as 3 servings (meal prep).
* A recipe is used at most twice a week, or more only if there are too few recipes to fill the week.
* If even the lowest-cost week is over budget, that week is shown with how far over it is (Gherkin "Budget too
  low").
* Otherwise, with macro targets, each day takes the best-fitting recipe that still leaves the rest of the week
  affordable. That invariant guarantees the plan never exceeds a feasible budget. Fit is a weighted relative
  error, with protein weighted 2x.
* Prices are `Decimal` dollars rounded to cents.

**Graceful degradation.** Any failure from the recipe source becomes `MealPlanResult(plan=None)`, and the page
shows "Meal suggestions are temporarily unavailable" with a link back to the dashboard. That satisfies the
customer requirement that core workout features keep working when a third-party API fails. Failures include
network errors, timeouts, HTTP 401/402/5xx, malformed JSON, no usable recipes, and a missing key.

**Spoonacular adapter.**
* It calls `GET /recipes/complexSearch` with `type=main course&sort=price&sortDirection=asc&addRecipeNutrition=true&number=40`,
  using stdlib `urllib` (no new dependency).
* There is a 5-second timeout, and responses are capped at 2 MB.
* The key is sent in the `x-api-key` header, never in the URL, so it can't leak through logs or error messages.
* `pricePerServing` is read as US cents.
* Each item is validated individually: malformed items, non-gram nutrients, and non-positive or non-finite values
  are skipped. Only `https://` image and source URLs from Spoonacular's hosts are kept.
* The query does not depend on the user, so one result is cached for 12 hours and serves everyone. No user
  action can trigger extra billed calls.
* Failures are cached for 2 minutes so a down or over-quota API isn't retried on every page view.
* The page credits Spoonacular when it is the source.

## What this offers
* **Plug-and-play with D-4 and D-6.**
  * Macro targets arrive through one method and one setting. The planner already accepts per-day targets.
  * The grocery list (D-6) should call `weekly_meal_plan` rather than reimplementing planning.
* **Testable without a network or D-4.** The planner is unit-tested with boundary values and a seeded
  brute-force comparison (swebook ch. 10). Adapters are tested with a fake HTTP layer. Views and Gherkin
  scenarios swap in the fakes in `nutrition/testing.py` (`FixedRecipeSource`, `UnavailableRecipeSource`,
  `FixedMacroTargets`).
* **Works today without an API key.** The default starter catalog needs no secret, so CI, local development, and
  production run without new infrastructure.
* **Security:**
  * The page reads only the signed-in user's own budget.
  * Users can't trigger outbound requests or vary the query.
  * The API key stays server-side and out of URLs and logs.
  * Third-party strings are auto-escaped, and third-party URLs are allow-listed.

## Tradeoffs considered
* **Persist the generated plan in the database:** gives a stable week and a direct input for D-6. Deferred, because
  the planner is deterministic for the same recipes and budget, so a plan only changes when the cached catalog
  refreshes or the budget changes. Revisit when D-6 needs a fixed shopping list for the week.
* **Optimal solver (integer programming):** would give a provably best macro fit within budget. Rejected for now
  because it adds a dependency and cost. The greedy approach is simple, deterministic, and guarantees the budget.
  It is not guaranteed to find the single best fit.
* **Fall back to the starter catalog when Spoonacular fails:** hides outages and silently changes prices. The
  Gherkin scenario asks for an explicit "temporarily unavailable" state, so we show that instead.
* **`requests`/`httpx`:** nicer APIs, but stdlib `urllib` covers one GET with a timeout. AGENTS.md prefers no new
  dependency when the standard library suffices.
* **Shared cache:** Django's default local-memory cache is per pod, so each of the 2 replicas makes its own call
  every 12 hours. That is acceptable for the quota. A shared cache would be new infrastructure.

**Known limitations and follow-ups:**
* "This Week" and starting a workout belong to D-3. Until it lands, the unavailable notice links to the
  dashboard, which is the home screen today. The Gherkin step checks that link and that the dashboard still loads.
* Turning on Spoonacular in production needs `spoonacular-api-key` added to Secret Manager (Terraform), to the
  SecretProviderClass, and `RECIPE_SOURCE=spoonacular` in the Deployment's environment. That is the
  infrastructure owner's change.
* Starter catalog prices are estimates and should be reviewed each semester.
* Without macro targets, plans optimise for cost only, so a large budget is not "spent" on more protein.
