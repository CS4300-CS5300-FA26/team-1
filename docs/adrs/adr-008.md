# Build the weekly meal plan around connectors to the features built alongside it
Date: 2026-10-31

## Status
Accepted

## Decision
Story D-5 (weekly budget meal plan, issue #10) lives in the `nutrition` app. Sprint 2 builds four related features
in parallel: D-3 workouts, D-4 macro targets, D-5 meal plan, and D-6 grocery list. So D-5 owns only what the story
asks of it, and reaches everything else through **connectors**. A connector is an interface D-5 defines plus a
setting naming the class that implements it ([dependency inversion](https://www.swebook.org/chapters/06-design-and-architecture/)).
A teammate plugs their feature in by writing that class and changing one setting; no meal plan code changes.
Until then, each connector has a "not connected yet" default and the meal plan falls back to a sensible default,
saying so on the page. No number is guessed: nutrients come from USDA data, targets from the published FDA Daily
Values, and prices only from D-6.

**Planning rules.**
* **Portions:** each planned meal gets one recipe at 1, 1½, or 2 servings, so days can actually reach their targets.
  Breakfasts come from breakfast recipes; lunches and dinners from mains.
* **Variety:** a recipe is used at most twice a week ("cook once, eat twice") and never twice in a day. The limits
  loosen only if there are too few recipes.
* **Macro fit:** each day is matched as closely as possible to that day's targets (D-4 can give rest days lower
  carbs), scaled to the meals planned: each meal covers a third of the day. Closeness is the sum of the relative
  misses on protein, carbohydrate, and fat.
* **Holistic cost:** with prices, the week is costed the way it's bought. Every ingredient is rounded up to whole
  packages, so meals that share ingredients cost less and the planner looks for that overlap.
* **Budget:** with a budget, staying within it comes first. If no plan fits, the cheapest plan found is shown with
  how far over it is (Gherkin "Budget too low").
  While over budget, plans that use less food (weight times price) are preferred next, so the search walks down to
  the next whole-package saving instead of stalling just above one.
* **New plan:** "Generate a new meal plan" avoids the previous plan's recipes where that costs nothing more.
* **Search:** a seeded local search over single-meal swaps and recipe-wide swaps (swapping a recipe everywhere it
  is used, so an ingredient can drop out entirely), restarted six times. It takes about 0.4 s, and only when a
  plan is made. Unit tests check it against brute force on small cases.

### Acceptance (issue #10) and fallbacks
`features/meal_plan.feature` holds the three issue scenarios, using the connectors' test stand-ins in
`nutrition/testing.py`. It adds two fallback scenarios: no personal macro targets yet, and no grocery prices yet.

## What this offers
* **Independent work.** Each teammate's feature plugs in through one class and one setting. Until then, D-5 still
  plans real weeks with real nutrition data.
* **No made-up numbers.** Nutrients and portion weights cite USDA FoodData Central ids, the fallback targets are a
  published federal standard, and costs come only from D-6's prices. Each fallback is stated on the page.
* **Grocery-aware costs.** Whole-package costing rewards meals that share ingredients, so the estimate is close to
  what the shopping list costs.
* **Safe by default.**
  * Plans are per user (unique per user per week), and the page reads only the signed-in user's profile and plan.
  * Selections from the query string are allow-listed and never echoed, and the only action is a CSRF-protected
    POST that redirects to allow-listed values.
  * Third-party connectors can't take the page down: their exceptions are caught, logged, and fall back.
  * Nothing calls the network at runtime, and no API key or secret is needed.
* **Testable.** The planner is pure, every connector has test doubles, and the browser tests cover the keyboard,
  no JavaScript, and phone and wide layouts.

## Tradeoffs considered
* **A recipe API (Spoonacular), as first implemented:**
  * The free plan is 50 points a day; one plan plus its details used about 30.
  * Its terms allow caching for at most one hour, which conflicts with storing a week's plan.
  * The customer confirmed it isn't required.

  The recipe source is still a connector, so an API could be added later.
* **Prices in the catalog (BLS averages plus estimates):** rejected. Most would have been guesses, and prices
  belong to D-6. Averaging D-6's quotes keeps the meal plan and the grocery list consistent.
* **An exact optimizer (integer programming, for example `scipy.optimize.milp`):** it would prove the plan is the
  cheapest and best-fitting possible, but it adds a large dependency. The local search is deterministic, fast, and
  matches brute force on small cases. This is a follow-up if plan quality needs to be proven.
* **A seven-column week grid of every meal:** tried first. It was cramped (21 recipe names at once), and choosing
  a meal jumped to its details at the bottom of the page. A week strip plus one day at a time, with recipes opening
  in place, keeps the whole week one tap away without either problem.
* **Per-meal shares of the day (25/35/40):** rejected as an invented split. Meals are fitted at the day level,
  each covering an equal third.
* **Storing plans as catalog foreign keys:** would tie stored plans to one recipe source. A source id keeps the
  connector replaceable; if a recipe disappears, the plan is simply remade.
* **Seeding with a data migration:** it would run against historical models and break fresh migrations after
  schema changes. Loading after `migrate` always uses the current models.

**Known limitations and follow-ups:**
* The catalog has 25 recipes. Dietary filters (vegetarian, allergens) need more recipes and tags.
* SR Legacy dates from 2018. FoodData Central's Foundation Foods could replace it item by item, keyed by FDC id.
* The Daily Values are general, not personal; D-4 replaces them. Exceeding a target counts as a miss just like
  falling short.
* Pantry staples (salt, spices) aren't weighed, priced, or counted in nutrition.
* "Today" and the week boundary use the server's time zone (UTC).
