# Build the weekly meal plan as a pure planner behind two swappable ports
Date: 2026-10-29

## Status
Accepted

## Decision
Story D-5 (weekly budget meal plan) lives in a new `nutrition` app, split so that the parts likely to change are
hidden behind small interfaces. This follows the information-hiding and dependency-inversion guidance in
[swebook.org chapter 6](https://www.swebook.org/chapters/06-design-and-architecture/).

| Module | Responsibility (its "secret") |
| --- | --- |
| `nutrition/domain.py` | Immutable value types: `Recipe` (with its course), `RecipeDetails`, `MacroTargets`, `PlannedMeal`, `PlannedDay`, `MealPlan`. No Django imports |
| `nutrition/planner.py` | The planning rules (pure, deterministic, no I/O) |
| `nutrition/ports.py` | The two interfaces the planner needs, `RecipeSource` and `MacroTargetsProvider`, and the loader that picks implementations from settings |
| `nutrition/recipe_sources.py` | Adapters: `StarterCatalogSource` (bundled JSON, no network) and `SpoonacularRecipeSource` |
| `nutrition/cache.py`, `nutrition/models.py` | A shared cache for recipe API data in Postgres (`RecipeCacheEntry`) |
| `nutrition/macros.py` | `NoMacroTargets`, a placeholder until D-4 |
| `nutrition/plan_store.py`, `SavedMealPlan` | Versioned JSON snapshots of a plan; a user's saved plan per week |
| `nutrition/report.py` | Report figures (budget use, daily spend, ingredients) and the ingredients CSV (pure) |
| `nutrition/services.py` | The use cases: `current_meal_plan`, `save_meal_plan`, `generate_new_meal_plan`, `discard_draft`, `weekly_meal_plan`, `meal_details` |
| `nutrition/views.py` | `/meal-plan/` (page), `/meal-plan/details/` (one meal's details panel), `/meal-plan/save/`, `/meal-plan/new/`, `/meal-plan/discard/` (POST), `/meal-plan/report/` and `/meal-plan/report/ingredients.csv` |

**Plug-in points.** Both are dotted paths in settings, so swapping an implementation changes no planner code:
* `NUTRITION_MACRO_TARGETS_PROVIDER`
  * D-4 (macro generation) adds a class with `weekly_targets(user, week_start) -> 7 daily MacroTargets | None`
    (Monday first, so rest days can have lower carbs) and points this setting at it.
  * Until then plans are optimised for cost alone, and the page says so.
  * A provider that returns a malformed week is logged and ignored.
* `NUTRITION_RECIPE_SOURCE`
  * Chosen with the `RECIPE_SOURCE` environment variable: `catalog` (default) or `spoonacular`, which needs
    `SPOONACULAR_API_KEY` or the `spoonacular-api-key` mounted secret.
  * A source provides `budget_recipes()` (breakfast and main recipes with price and macros) and
    `recipe_details(recipe)` (ingredients, steps, time, source link).
  * It returns validated domain objects or raises `RecipeServiceUnavailable`.
  * Under `manage.py test`/`behave`, settings force the catalog and a blank key, so tests can never reach the
    network or spend quota, whatever `.env` says.

**Meals and planning rules.**
* Onboarding asks which meals to plan (`UserProfile.meal_pattern`): breakfast, lunch and dinner; breakfast and
  dinner; lunch and dinner; or dinner only. Users who onboarded earlier get all three.
* Each meal is one serving. Breakfasts come from breakfast recipes, lunch and dinner from mains.
* **Every meal in the week is a different recipe**, which gives users the widest choice. A recipe repeats only
  if a source has too few recipes to fill the week, and then as evenly as possible.
* A day's macro targets are split across its meals 25/35/40 (breakfast/lunch/dinner), renormalised for the
  meals chosen. For example, breakfast and dinner get 38%/62%.
* If even the lowest-cost week is over budget, that week is shown with how far over it is (Gherkin "Budget too
  low").
* Otherwise, with macro targets, each meal takes the recipe that best fits its share of the day while the rest of
  the week can still be bought within budget. That invariant guarantees the plan never exceeds a feasible budget.
  Fit is a weighted relative error, with protein weighted 2x.
* Prices are `Decimal` dollars rounded to cents. A missing or negative budget counts as $0, which still gets the
  lowest-cost week with the whole cost shown as the shortfall.

**Saving a week, and generating a new plan.**
* The plan a user sees this week is chosen in this order:
  1. their unsaved **draft**, kept in the server-side session, if it still matches their week, budget, and meals;
  2. else the plan they **saved** for this week (`SavedMealPlan`, one row per user per Monday, `saved_at`
     timestamp);
  3. else a freshly generated plan, which becomes the draft.
* "Save meal plan" stores the current plan as that week's `SavedMealPlan` and clears the draft. A new week starts
  fresh.
* "Generate a new meal plan" replaces the draft with a plan built with `avoid`: recipes already shown this week
  (tracked in the draft) are used only when nothing else fits. It still keeps to the budget and "every meal
  different".
* "Back to saved plan" drops the draft.
* All three actions are POST with CSRF. They redirect back to the selected day and meal using allow-listed values
  only.
* Plans are stored as **snapshots of validated domain data** with a format version, not as recipe ids. A saved
  week therefore stays the same when the recipe cache refreshes or a recipe disappears from the source.
* Loading a snapshot rebuilds and re-validates the domain objects. A snapshot that doesn't fit (old version,
  edited) is ignored, and the user gets a fresh plan instead of an error.
* The draft lives in the database-backed session, so users can't tamper with it.

**Report.** `/meal-plan/report/` summarises the plan the user is currently seeing:
* **Budget:** one hero figure (the estimated weekly cost) and a **meter** against the budget.
  * The fill shows state (accent within budget, danger when over), on a track that is a lighter step of the same
    hue.
  * A status line says "Within budget… / Over budget by…" in words, with an icon.
* **Key-number tiles:** budget, planned spend, daily budget, and number of meals.
* **Daily spend:** horizontal bars on one shared scale, with a line marking the daily budget (budget ÷ 7).
  * Bars are ≤24px with a rounded value end and a square baseline, and the value sits at the bar's end.
  * A table view (day, meals, cost, % of daily budget, protein) carries the same data for screen readers. On
    phones it scrolls inside a focusable, labelled region.
  * These follow the team's data-visualisation rules (meter for one value against a limit; single series in one
    hue with no legend; no dual axes).
* **Ingredients:** grouped by day in collapsible sections, plus a CSV download.

**Ingredients CSV security** (`/meal-plan/report/ingredients.csv`):
* Login and onboarding are required, and it only ever contains the signed-in user's current plan.
* It is read-only (GET), with no user input.
* Every cell that starts with `=`, `+`, `-`, `@`, tab, or CR is prefixed with `'`, so spreadsheet apps show it as
  text instead of running it as a formula (CSV/formula injection). Recipe titles and ingredients come from a third
  party.
* Headers:
  * `Content-Type: text/csv; charset=utf-8` with `nosniff` (global), plus a UTF-8 BOM for Excel.
  * `Content-Disposition: attachment` with a filename built only from the week's date.
  * `Cache-Control: private, no-store`.

**Page.**
* A day picker (previous/next arrows around the day name, plus a button per day) defaults to today.
* A toolbar shows whether the plan is saved (badge with timestamp) and offers Save, Generate a new meal plan,
  Back to saved plan, and View report.
* The selected day's meals are listed on the left. The selected meal's details appear beside them in a **sticky,
  height-capped panel** that scrolls on its own on wide screens, so long recipes never stretch the page past the
  list. The details are:
  * the image, at-a-glance chips (cost, time, ingredient count), and protein/carbs/fat tiles (with a bar against
    the meal's target once there are targets);
  * **Ingredients and Steps tabs** (a two-column ingredient list, and numbered steps on a timeline);
  * a link to the original recipe.
* Images are a photo laid over **course-tinted placeholder artwork** (an egg for breakfast, a bowl for mains). The
  photo is decorative (`alt=""`), so if it is missing or fails to load the artwork shows, with no JavaScript
  needed.
* Every control is a plain link (`?day=&meal=`), so the page works without JavaScript.
* `nutrition/static/nutrition/meal_plan.js` switches days instantly (all seven days are in the page) and swaps in
  details from `/meal-plan/details/` without a reload.
  * Focus moves to the details heading, and if a request fails it falls back to a normal page load.
  * It runs the tabs (WAI-ARIA tabs pattern: one tab stop, arrow keys, Home/End). Without JavaScript both sections
    show under their own headings.
* The fragment endpoint only serves meals from the signed-in user's own plan, and returns 404 otherwise.
* Reusable theme components were added for these pages:
  * layout: `day-picker`, `split`, `panel`/`panel--sticky`, `toolbar`, `media--link`, `food-image`;
  * small pieces: `chip`, `macro-grid`, `tabs`, `ingredient-grid`, `steps`, `status-badge`, `stat`;
  * report: `hero-figure`, `meter`, `bar-list`, `stat-row`/`stat-tile`, `data-table`, `table-scroll`,
    `disclosure`, `messages`.
  * Chart and placeholder colours are theme tokens with light and dark values. Data-driven widths are SVG
    attributes, so there are no inline styles.

**Graceful degradation.**
* If the recipe search fails, the page shows "Meal suggestions are temporarily unavailable" with a link back to the
  dashboard. That satisfies the customer requirement that core workout features keep working when a third-party
  API fails.
* If only details fail, the plan still shows and the details panel says ingredients and instructions are
  temporarily unavailable.
* Failures include network errors, timeouts, HTTP 401/402/5xx, malformed JSON, no usable recipes, and a missing key.

**Spoonacular adapter and quota.**
* **Calls:**
  * Two searches: `GET /recipes/complexSearch?type=breakfast|main course&sort=price&sortDirection=asc&addRecipeNutrition=true&number=40`.
  * One details call per opened recipe: `GET /recipes/{id}/information?includeNutrition=false`.
* **Limits:** stdlib `urllib` (no new dependency), a 5-second timeout, and responses capped at 2 MB.
* **API key:** sent in the `x-api-key` header, never in the URL, so it can't leak through logs or error messages.
* **Search validation:**
  * `pricePerServing` is read as US cents.
  * Malformed items, non-gram nutrients, and non-positive or non-finite values are skipped.
  * Only Spoonacular `https://` image URLs are kept.
  * A dish returned by both searches is kept once, under its first course.
* **Details validation:**
  * Only the structured `analyzedInstructions` steps are used; the free-text `instructions` field can contain
    HTML.
  * Text and list lengths are capped.
  * Only `https://` source links are kept.
* **Caching, in Postgres (`RecipeCacheEntry`), shared by every pod and kept across restarts:**
  * Only validated, trimmed data is stored, never raw responses.
  * Searches last 24 hours and serve everyone; the query doesn't depend on the user.
  * Details last 30 days, and only for recipes in the requesting user's own plan, so users can't trigger lookups
    of arbitrary recipes.
  * Failures are remembered for 2 minutes, so a down or over-quota API isn't retried on every request.
* **Expected use:** a few points a day for the searches, plus one point per newly opened recipe each month. That
  is well within the free plan.
* The page credits Spoonacular when it is the source.

## What this offers
* **Plug-and-play with D-4 and D-6.**
  * Macro targets arrive through one method and one setting. The planner already accepts per-day targets and
    splits them across meals.
  * The grocery list (D-6) should call `weekly_meal_plan` and `meal_details`. `RecipeDetails.ingredients`
    exists for it, and those details are already cached.
* **Testable without a network or D-4.**
  * The planner is unit-tested with equivalence classes and boundary values: budget at the lowest cost, one cent
    under, $0, $0.01, very large, and negative. A seeded brute-force comparison checks it (swebook ch. 10).
  * Adapters are tested with a fake HTTP layer.
  * Views, Gherkin scenarios, and Playwright browser tests (including a no-JavaScript run) use the fakes in
    `nutrition/testing.py`.
* **Works today without an API key.** The default starter catalog (9 breakfasts and 16 mains, with ingredients
  and steps) needs no secret, so CI, local development, and production run without new infrastructure.
* **Security:**
  * Pages read only the signed-in user's own budget, meals, and plan.
  * Users can't trigger arbitrary outbound requests.
  * The API key stays server-side and out of URLs and logs.
  * Third-party text is auto-escaped, and third-party URLs are allow-listed.

## Tradeoffs considered
* **Save every generated plan automatically:** simpler state, but users asked to choose when to keep a plan. An
  unsaved plan lives in the session until they save it.
* **Store saved plans as recipe ids and re-fetch the recipes:** smaller rows, but a saved week would change or break
  when the recipe source changes. Snapshots keep a saved week exactly as the user saw it.
* **Combine the ingredients into one shopping list in the report:** that is D-6 (grocery list), which needs unit
  parsing and merging. The report lists ingredients per meal; D-6 can build its merged list from the same
  `meal_details` data.
* **Optimal solver (integer programming):** would give a provably best macro fit within budget. Rejected for now
  because it adds a dependency and cost. The greedy approach is simple, deterministic, and guarantees the budget.
  It is not guaranteed to find the single best fit.
* **Prefetch details for every recipe at search time:** no details calls during page views, but it would spend
  quota on recipes nobody opens (about 80 per refresh). Lazy, long-cached details cost far less.
* **Django's cache framework:** the default local-memory cache is per pod and lost on restart. The database cache
  backend needs a `createcachetable` step outside migrations. A small model keeps everything inside
  `migrate`, which the deploy pipeline already runs.
* **Fall back to the starter catalog when Spoonacular fails:** hides outages and silently changes prices. The
  Gherkin scenario asks for an explicit "temporarily unavailable" state, so we show that instead.
* **A JavaScript carousel or framework:** links with a small enhancement script keep the page usable without
  JavaScript, with no build step or new dependency.

**Known limitations and follow-ups:**
* "This Week" and starting a workout belong to D-3. Until it lands, the unavailable notice links to the
  dashboard, which is the home screen today. The Gherkin step checks that link and that the dashboard still loads.
* Turning on Spoonacular in production needs `spoonacular-api-key` added to Secret Manager (Terraform), to the
  SecretProviderClass, and `RECIPE_SOURCE=spoonacular` in the Deployment's environment. That is the
  infrastructure owner's change.
* The adapter is built from the documented response shapes and tested against fakes; check it against the live
  API before relying on it.
* Starter catalog prices and macros are estimates and should be reviewed each semester.
* "Today", the week boundary, and the "Saved" timestamp use the server's time zone (UTC), which can differ from
  the user's local time.
* The report fetches details for every meal in the plan (cached for 30 days). With Spoonacular, a brand-new plan's
  first report view can cost up to one quota point per meal.
* Without macro targets, plans optimise for cost only, so a large budget is not "spent" on more protein.
